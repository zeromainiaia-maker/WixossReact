## 背景＝バグの正体

段2 の finding は**段1 で真バグと確定済み**です（疑いではない）。今回の81件はすべて
**「原文に書いてある発動条件・対象限定・期限が live JSON に存在しない」**型で、実害は2方向あります。

🔴**この形は逆翻訳・census・golden・smoke・fuzz が全部緑のまま意味が壊れます。** JSON に語彙が無いだけなので、どの計器も「無いもの」を見られません。

### 取る順（推奨）

1. **既存の受け皿に配線するだけで済むもの**＝`src/types/effects.ts` を grep して条件型・フィルタキーが既に在るもの。**ここが本体。**
2. **同じ根が複数 finding に出ているもの**＝`WXDi-P11-003-E1`（3件）・`WXDi-P08-048-E1`（2件）・`WXDi-CP02-001-E1`（2件）など。1効果を直すと複数閉じます。
3. **受け皿ごと無いもの**＝**直さずに報告だけ**してください（Claude が PLAN §5.3 へ `O-nn` で登録します）。

## 既存機構を最優先で流用すること

- 条件は **`Condition`（`evalCondition`）** と **`ActiveCondition`（`checkActiveCondition`）の別 union** です。**片側だけ足さない。**
- 対象限定は `TargetFilter`。`story` / `color` / `level` / `powerRange` / `cardNames` / `excludeSelf` / `thisCardOnly` などは既に在ります。
- 「この方法で処理したカードが〜の場合」は `LAST_PROCESSED_MATCHES`、「直前に選んだものを対象に」は `targetsLastProcessed`。
- **新しい型を乱立させない。** 新設が要ると判断したら、**その根拠（既存のどれを検討して、なぜ足りないか）を報告に書く。**

## ⚠️ ガードレール（CODEX_GUIDE §5 から該当分）

- **§5-1**：1効果ずつ原文照合してから条件を書く。**まとめて機械置換しない。**
- **§5-2**：engine の実装を読んで「本当に評価できるか」を確認してから採用する。parser が条件を吐いても engine が解決できないと**常時偽＝過小実行**になる。
