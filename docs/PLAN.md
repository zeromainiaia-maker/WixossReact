### 2.2 完了の定義

**⑤まで通って初めて「完了」**。④まで（ゲート緑）は**未完了**であり、「要実機検証」と書いて次セッションへ送ることは**しない**。

- **golden/smoke/fuzz が守れない層が実在する**＝`persist.commit` と React 反映のタイミング差、UI の選択リセット、モーダルの候補絞り込み。**この層の唯一の防御が実機シナリオ**（回帰トリップワイヤとして残す）。
- 1巡のスコープは**⑤まで1セッションで回せる大きさ**に切る。効果数で言えば **15〜20効果／バッチ**が目安（4効果のバッチは固定費を満額払って割に合わない・実測）。

### 2.3 実機検証を省略してよい唯一の条件

**実機から原理的に観測できないと分かっている**とき（例＝`optional`「〜してもよい」の【自】は CPU 側が自動応答するため画面に出ない）。このときは **golden で両方向を固定し、理由を §5.1 に `V-<次番号>` として登録**する。「時間がないから次回」は該当しない。

### 2.4 作業中にバグを見つけたとき

**その場で直すのが既定。**（Opus 単独運用になったので、旧「Sonnet が観測して積む → Opus が直す」の交互サイクルは廃止。常設受け口だった「Opusタスク12」も廃止＝在庫0で閉じた。）

### 4.2 実装 — 型・parser・engine

- 🔴**型を足すときは「型 ＋ 両評価器 ＋ golden」の3点セットで初めて1件完了。**`checkActiveCondition` は case の無い型を **`return true`＝無条件成立**に落とすので、**型だけ足すのは条件が無いのと同じか、それ以下**（条件つき常在能力が常時発動する）。しかも **smoke/census/fuzz は全部緑**のまま通る。
- 🔴**評価器も `matchesFilter` も2つある**＝`Condition`＝`execUtils.ts` の `evalCondition`／`ActiveCondition`＝`effectEngine.ts` の `checkActiveCondition`。**両方に入れないと片側だけ穴が空く。**
- ⚠**条件節は「場合」と「かぎり」で別の表に入る**（`STATE_CONDITION_CLAUSES_V2` ／ 先頭条件節テーブル）＝片方だけ直すと**同じ文型なのに一部だけ直らない**。「規則が無い」と「共通表に無い」は別物。
- ⚠**新しい語彙を足す前に「同義の別キー」を必ず探す**（`noGuard`/`hasGuard`、`eachDistinctLevel`/`selectionConstraint.distinct`、`IS_SELF_CHARMED`/`THIS_CARD_IS_CHARMED` ＝**同型・同実装の別型**）。3例以上の前例がある。
- ⚠**「機構が無い」と決めつける前に timing 別の類似フィールドを全部探す**（発生源クラス限定は `trashSourceStory`／`banishedSourceStory`／`powerDecreaseSourceStory`／`milledSourceStory` の**4本が既にあった**）。
- 🔴**1つの根から過剰実行と過小実行が同時に出る。**条件が消えるだけでなく、条件節の中のクラス修飾が**直前の対象へ誤付着**する。**条件だけ足すと過小実行が残り、誤付着だけ消すと過剰実行になる＝片方だけ直してはいけない。**
- ⚠**部分 filter だけを採用しない**＝同一の対象に2系統が掛かる形（`WXEX2-06`）では、片方だけ載せると原文と逆の過小実行になる。ただし**別ステップの別対象**なら片方だけ直してよい。
- ⚠**同語の別用法を filter にしない。** 状態語（チャーム／アクセ／凍結等）は **①対象フィルタ ②効果元の自己条件 ③装着ホスト参照**の3用法に分岐する。付与文・条件節・リマインダー文を filter にすると**原文と逆の過小実行**になる。⚠**「アップ状態のルリグN体をダウンする：」は使用コスト**であって対象フィルタではない（9件中8件がコスト側だった）。

- 🆕🔴**引用「…」の中のトリガー句を外側の regex で拾わない**（2026-08-24・`O-55`）＝【常】ブロックの分岐が「このシグニがバニッシュされたとき」を**引用の内外を区別せず**拾い、`effectType` を AUTO へ倒して本文を引用の中身へ差し替えていた＝**外側の付与宣言が丸ごと消えて内側だけが自分の能力になる**（`WXDi-D09-P18-E1` は `POWER_MODIFY` だけになっていた）。判定は**開き括弧の数**（`「『` と `」』` の出現差）で内外を見る。⚠同じ理由で**引用付与の解析は条件抽出ループより前に置く**（`parseActiveCondition` が引用内の「〜されたとき、」を先に食うと `^` アンカーが外れて丸ごと取り逃す）。

### 4.3 計器の読み方

- ⚠**`census` に残っている＝バグ、ではない。** 実測で残りの約3割が**計器側の対応語彙漏れ**（部分一致なので大文字小文字で穴が空く）。**較正は実装より安い**ので先に取る。⚠ただし**較正は「実バグが減った」ではない**＝母集団から偽陽性が抜けただけで、実バグの絶対数は変わらない。
- ⚠**`census:wiring` の miss 数は「1本直せば N 件直る」ではない。** 効果は持っている入口ラベル全部のセルに計上される（**クロス計上**）＝「原文にフレーズはあるが同じ効果の**別の入口**に掛かっている」ものが関係ないセルにも出る。**`--cell` で原文を全部読んで、真の脱落／クロス計上／条件節用法／コスト側フィルタに仕分けてから配線する。miss 数は「掘る価値の指標」であって「見込み件数」ではない。**
- ⚠**`census:wiring` は `has===0` の語彙を表から捨てる**＝**正規表現を絞りすぎると穴ごと不可視になる**（`hasAcce` の除外を広く書いたら has が落ちて穴が消えた実測あり）。**「census:wiring が0件だから穴はない」と読んではいけない。**
- ⚠**`census:stubs` の「STUB＝未実装」ではない**＝実装済みハンドラの表示名でもある。**新しい綴りを足す前に、同義の STUB が engine に無いかを必ず見る。**
- ⚠**`docs/_partial_report.txt` を「直すべきリスト」として読まない**＝刻印は *fresh parse* の記録で、live が `MANUAL` なら既に解消済み（40件中38件がそれだった）。
- 🔴**既存の計器に映らない穴が1種類ある**＝**「受け皿（型・engine）はあるのに parser が配線していない」**。`census` にも `census:wiring` にも出ない。🆕**2026-08-24 続き640 の `O-53` はさらに悪い型**＝**逆翻訳が原文どおり正しいのに engine だけが別のゾーンを読む**（`LOOK_AND_REORDER` の `source.location:'hand'` が `state.deck` へ暗黙フォールバック）―**逆翻訳・census・golden・smoke・fuzz の全部が緑のまま16効果が壊れていた**。⚠**型の union にある値を executor が全部分岐しているか**はどの計器も見ていない（三項演算子の else に落ちる形）。**7回連続で当たった型**なので、「型はあるが live 利用が極端に少ない語彙」を数える計器は最優先の在庫（未着手）。
- 🆕🔴**逆翻訳がカード全文 regex から描いている STUB は、計器として嘘をつく**（2026-08-24・`O-55`）＝`PLACE_TRAP_OPTIONAL` の表示は原文をそのまま切り出していたので、**JSON が出所（どこから設置するか）を1つも持っていなくても逆翻訳シートは緑**だった。**逆翻訳は必ず JSON のフィールドから描く**（§6.4 O-20 と同じ落とし穴）。engine 側が `ctx.cardMap` の `EffectText` を読んで分岐している STUB も同類で、**JSON を見ても何が起きるか分からない**（`TRAP_OPERATION`／`TRAP_OP`＝`O-56`）。
- ⚠**golden は「修正前データで実際に落ちるか」を確かめてから採る**＝フィルタ無しでも候補の先頭がたまたま正解で **vacuous に PASS** することがある。**対象を候補の先頭以外へ置く。**
- ⚠**枝の数を固定した golden トリップワイヤは、正しい是正でも落ちる**＝`join(',')` の完全一致ではなく「全エントリが opponent かつ1つ以上」のような性質で書く。

### 4.4 実機シナリオの罠（着手前に必読）

1. 🔴**`spec.hostSet`／`guestSet` の両方に `'field.check': null` を必ず入れる**＝`injectScenario` の `CORE_FIELD_KEYS` に `check` が含まれ**リセットされない**。前シナリオのライフクラッシュ確認モーダルが全画面を覆い**クリックが1つも通らない**（3回踏んだ）。⚠🆕**2026-08-24（続き637）＝引き継がれるのは `check` だけではない。`CORE_FIELD_KEYS`（`lrig` `signi` `assist_lrig_*` `check` `key_piece*` `free_zone` `beat_zone`）は全部そう**で、**使うシナリオが自分で書き切らない限り前シナリオの盤面が残る**。実例＝`guardExtraColorlessSufficient` が `field.signi` を固定しておらず、直前シナリオが置いた `WX18-039`（【常】レベル２と３でガード不可）が残って**手札の Lv2 サーバントが「正しく」候補から消え**、engine バグに見える FAIL になった。**盤面依存の判定をするシナリオは `field.*` を自分で固定する**。⚠**後始末も自分でする**＝ライフクラッシュを起こして抜けるシナリオは `field.check` を消化（「エナに送る」まで）してから返す。

### 4.5 修正を live へ届ける経路（届かないと恒久 no-op になる）

- 🔴**`build:effects` の収穫マージは `parseStatus:MANUAL`／`PARTIAL` の効果を不可侵にする**＝`manualEffects.ts` を後から直しても **live には永久に届かない**（新しい id の追加だけは通る）。届けるには **`npx tsx scripts/syncManualLive.ts <CardNum>`**。⚠実行後は必ず `npm run gates`（live を直接書くので、ゲートだけが安全網）。
- 🔴**parser を直したのに live が変わらないときは、まず3ファイルを見る**＝`docs/_held_fresh.json`／`_partial_fresh.json`／`_idset_fresh.json`。**id 集合が live と fresh でズレたカードは `_idset_fresh` に出る**（実測46カード）。
- 🆕🔴**`parseStatus:MANUAL` なのに `manualEffects.ts` に実体が無いカードがある**（2026-08-24・`O-54`＝`WXDi-P08-038`）＝過去の外科パッチが刻印だけ残した **live 限りの遺物**。この状態だと **`syncManualLive` は「同期元が無い」ので効かず**、`build:effects` はカード単位 PRESERVE で永久に凍る。**直し方＝`grep <CardNum> src/data/manualEffects.ts` が空なら、live の `parseStatus` を `AUTO` へ戻してから `build:effects`→`heldReview --adopt`**（以後 parser 改善が届くようになる）。⚠戻す前に **fresh が live の全情報を保っているか**を effectId のリーフパス単位で必ず確認する（本件は fresh が上位＝BURST の `isUp` 脱落まで同時に直った）。
- ⚠**`manualEffects.ts` のトップレベル効果は `MANUAL` か `PARTIAL` のみ**（`AUTO` と書くと `manual-fields` ゲートが exit 1）＝`mergeManualEffects` は `parseStatus` を見ず effectId 一致で常に manual 側を勝たせるので、`AUTO` の手書きコピーは **parser の最新出力を永久に上書きし続ける**。
- ⚠**`build:effects` は破壊的ではない**（curated は温存され、`heldReview --adopt` で明示採用したものだけが変わる）。正しい規律は「実行禁止」ではなく**「実行後に effectId 単位で全数比較して、意図した件数だけが変わったことを確認する」**（出力は minified 1行なのでテキスト diff は役に立たない）。
- ⚠**カード単位 PRESERVE で held に載らない効果**（同居効果が MANUAL 等）は `build` では直せない＝`effectId` をアンカーにした**外科パッチ**で JSON を直接訂正する。共有関数にカード固有テーブルを埋めるのは禁止。
