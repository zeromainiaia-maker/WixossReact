### 4.2 実装 — 型・parser・engine

- 🔴**型を足すときは「型 ＋ 両評価器 ＋ golden」の3点セットで初めて1件完了。**`checkActiveCondition` は case の無い型を **`return true`＝無条件成立**に落とすので、**型だけ足すのは条件が無いのと同じか、それ以下**（条件つき常在能力が常時発動する）。しかも **smoke/census/fuzz は全部緑**のまま通る。
- 🔴**評価器も `matchesFilter` も2つある**＝`Condition`＝`execUtils.ts` の `evalCondition`／`ActiveCondition`＝`effectEngine.ts` の `checkActiveCondition`。**両方に入れないと片側だけ穴が空く。**
- 🆕🔴**「自分で対象を決める」印は、汎用の対象ガードより先に読む**（2026-09-04 第105バッチ・`V-133`②で実証）＝
  `targetsTriggerSource` / `targetsLastProcessed` / `targetsStored` は **`target` が無くても対象が決まる**。
  ハンドラ冒頭に `const tgt = a.target ?? …; if (!tgt) return done(ctx);` を置くと、
  **その印だけを持つ宣言が無言 no-op** になる（`execGrantProtection` が実際にそうなっており、
  `WX20-056-E2` の「手札に戻らずダウンせず」が1度も付いていなかった）。
  🔑**同じ family でも1本だけ順序が違うことがある**（`execGrantKeyword` / `execGrantEffect` は正しかった）＝
  **新しい印を足したら、その印を読む全ハンドラで「ガードより前か」を grep で確かめる。**
  🔑**この形は「半分だけ動く」ので計器に映らない**（同居する別ステップが効いていると、ログも盤面も
  それらしく見える）＝**逆翻訳・census・golden・smoke・fuzz が全部緑のまま。実機だけが捕まえた。**
- 🆕🔴**「〜してもよい」を足すときは必ず入れ子にする**（2026-09-07 第209バッチ・`WX10-015-E1`）＝
  `STUB{OPTIONAL_ACTIVATE}` の「やらない」は `execSequence` の **Pattern ⑤ がその SEQUENCE の残りステップを全部捨てる**。
  同じ文型が1つの効果に**2回**あるとき（「自分のライフを見る…もよい。相手のライフを見る…もよい」）、
  平らに置くと**自分側を断った瞬間に相手側の処理まで消える**＝**過剰実行を直して過小実行を作る**。

### 4.3 計器の読み方

- 🔴🆕**golden のラチェットが落ちると、そのテストが途中で abort して POOL カーソルが変わり、
  *無関係な後続テスト*まで赤くなる**（2026-09-05・§5.3 `O-257` で実測）＝
  `eq()` は throw するので、失敗した assert より後の `fresh()` / `mkState()` が実行されず、
  **以降のテストが引くカードが1枚ずつずれる**。実際に `WXDi-CP02-036-E1` の E2E が
  「3体すべて消えるはずが1体残る」で落ち、engine の回帰を疑って時間を溶かした。
  ⇒ **FAIL が2件以上出たら、まず「上の方の1件」だけ直してもう一度回す。**
  同時に読むのは、それぞれが独立だと確かめてからにする。
- 🔴🆕**`scripts/` の重複 import は typecheck も golden も通る**（同上の巡で実測）＝
  `goldenTest.ts` に `finalizeUsedCardPlacement` の import を**二重に**足してしまったが、
  `npm run typecheck` は `scripts/` を見ず（既知）、`tsx`（esbuild）は重複を黙って畳むので**どのゲートも緑**だった。
  ⇒ **`scripts/` へ import を足すときは、まず `grep -c` で既存を数える。**
- 🆕🔴🔑**census を減らすときの手順（2026-08-30 続き739〜741 で確立・3巡で 460→245／較正 -173・実装 -42）**

  （引数なし＝カテゴリ別の型名・キー名の頻度表／`<カテゴリ名の一部>` ＝そのカテゴリを原文 × live JSON で全数 dump）。

  2. 🔑**JSON の「型名」と「キー名」を縦に並べて集計する**（2件以上に出る名前を数える）。
     **同じ名前が縦に並んだら実装ではなく較正**＝計器が受け皿の綴りを知らないだけ。
     実測でこれが **40／25／16／12／9／9／7／7／6／5…** の塊を出した（合計173）。

  4. **較正の前後で高シグナル id 集合を機械差分**し、「**消えた分＝目視した分／新規流入0**」を確認する。

- 🆕🔴**較正は必ず narrow ＋ 残渣チェック**＝「その節を除いた**残り**に語が残るならフラグを維持する」。
  **キー表に足すだけで済ませない**（例＝`*SourceStory` は `extraOk` にした＝「＜X＞の効果で発火」と

  `LastProcessed`（大文字 L）/ `LRIG_TO_DECK` / `NAME_CONTAINS` / `whenPowerZero` …。

  **カード名の一部**に当たっていた。**キー名だけでなく原文正規表現も疑う。**
- 🆕🔴**「兄弟効果（`-E1b` / `-E1c`）」は census を二重に汚す**＝あれは**1つの原文ブロックを2レコードに割った断片**で、

- 🆕🔴🔑**「census に残っている＝直すべき」でもない**（2026-08-31 続き744 で実測）＝**先行セッションが理由つきで

- ⚠**`census:wiring` は `has===0` の語彙を表から捨てる**＝**正規表現を絞りすぎると穴ごと不可視になる**（`hasAcce` の除外を広く書いたら has が落ちて穴が消えた実測あり）。**「census:wiring が0件だから穴はない」と読んではいけない。**
- ⚠**`census:stubs` の「STUB＝未実装」ではない**＝実装済みハンドラの表示名でもある。**新しい綴りを足す前に、同義の STUB が engine に無いかを必ず見る。**
- ⚠**`docs/_partial_report.txt` を「直すべきリスト」として読まない**＝刻印は *fresh parse* の記録で、live が `MANUAL` なら既に解消済み（40件中38件がそれだった）。
- 🔴**既存の計器に映らない穴が1種類ある**＝**「受け皿（型・engine）はあるのに parser が配線していない」**。`census` にも `census:wiring` にも出ない。🆕**2026-08-24 続き640 の `O-53` はさらに悪い型**＝**逆翻訳が原文どおり正しいのに engine だけが別のゾーンを読む**（`LOOK_AND_REORDER` の `source.location:'hand'` が `state.deck` へ暗黙フォールバック）―**逆翻訳・census・golden・smoke・fuzz の全部が緑のまま16効果が壊れていた**。⚠**型の union にある値を executor が全部分岐しているか**はどの計器も見ていない（三項演算子の else に落ちる形）。**7回連続で当たった型**なので、「型はあるが live 利用が極端に少ない語彙」を数える計器は最優先の在庫（未着手）。
- 🆕🔴**逆翻訳がカード全文 regex から描いている STUB は、計器として嘘をつく**（2026-08-24・`O-55`）＝`PLACE_TRAP_OPTIONAL` の表示は原文をそのまま切り出していたので、**JSON が出所（どこから設置するか）を1つも持っていなくても逆翻訳シートは緑**だった。**逆翻訳は必ず JSON のフィールドから描く**（§6.4 O-20 と同じ落とし穴）。engine 側が `ctx.cardMap` の `EffectText` を読んで分岐している STUB も同類で、**JSON を見ても何が起きるか分からない**（`TRAP_OPERATION`／`TRAP_OP`＝`O-56`）。
- 🆕🔴**「N セッション連続で同じ FAIL が再現する」は「本物のバグ」の証拠ではない**（2026-08-29・`V-89`）。
  `lookReorderCanTrash` は**4セッション連続で同じ数字（`hDeck=2 hTrash=3`）で FAIL** し、そのたびに
  「`git stash` しても HEAD で FAIL＝本セッション起因ではない」と正しく確認されて次へ送られていた。
  **真相は「シナリオが assert している UI が live にもう存在しない」＋「spec の deck に候補カードが1枚も無い」**で、
  **あの数字こそ仕様どおりの挙動だった**。⇒ **FAIL を寝かせる前に、まず「live JSON を読み直して、
  シナリオが assert している形が今も出るか」を確かめる**（§4.1「実測そのものが嘘をつく」の実機版）。
  ⚠**「HEAD でも再現する」は「engine のバグである」を意味しない**＝計器が古いときも同じ見え方をする。
- ⚠**golden は「修正前データで実際に落ちるか」を確かめてから採る**＝フィルタ無しでも候補の先頭がたまたま正解で **vacuous に PASS** することがある。**対象を候補の先頭以外へ置く。**
- ⚠**枝の数を固定した golden トリップワイヤは、正しい是正でも落ちる**＝`join(',')` の完全一致ではなく「全エントリが opponent かつ1つ以上」のような性質で書く。


- 🔴🆕**census の較正キーは「免罪符」になる**（`O-132`・第181バッチ／旧 PLAN §5.3 から移設）＝
  キーを表に足して黙らせると、**そのキーが JSON から消えても census は静かに合格し続ける**。
  実例＝「それぞれ１枚まで」は `PLAY_FREE` 2本で表され、`execPlayFree` が最後に `SEARCH{maxPick:1}`
  （0枚選択で確定できる）を出す＝**`PLAY_FREE` それ自体が「1枚まで」の上限スロット**なので上限キーは構造上いらない。
  ⇒ **キー表には足さず**、`extraOk` の残渣チェック（need ≤ slots）に slot として1つ数えて払い戻した
  （足すと「同じ効果の別アクションにある『N体まで』の脱落」まで隠れる）。
  🔑**較正したら必ず golden に「較正の根拠キーが live に実在する」を追加する**＝
  根拠が消えても計器が黙らないようにする（反転確認＝根拠キーを壊すと golden が FAIL）。

### 4.5 修正を live へ届ける経路（届かないと恒久 no-op になる）

- 🔴**`build:effects` の収穫マージは `parseStatus:MANUAL`／`PARTIAL` の効果を不可侵にする**＝`manualEffects.ts` を後から直しても **live には永久に届かない**（新しい id の追加だけは通る）。届けるには **`npx tsx scripts/syncManualLive.ts <CardNum>`**。⚠実行後は必ず `npm run gates`（live を直接書くので、ゲートだけが安全網）。
- 🔴**parser を直したのに live が変わらないときは、まず3ファイルを見る**＝`docs/_held_fresh.json`／`_partial_fresh.json`／`_idset_fresh.json`。**id 集合が live と fresh でズレたカードは `_idset_fresh` に出る**（実測46カード）。
- 🆕🔴**`parseStatus:MANUAL` なのに `manualEffects.ts` に実体が無いカードがある**（2026-08-24・`O-54`＝`WXDi-P08-038`）＝過去の外科パッチが刻印だけ残した **live 限りの遺物**。この状態だと **`syncManualLive` は「同期元が無い」ので効かず**、`build:effects` はカード単位 PRESERVE で永久に凍る。**直し方＝`grep <CardNum> src/data/manualEffects.ts` が空なら、live の `parseStatus` を `AUTO` へ戻してから `build:effects`→`heldReview --adopt`**（以後 parser 改善が届くようになる）。⚠戻す前に **fresh が live の全情報を保っているか**を effectId のリーフパス単位で必ず確認する（本件は fresh が上位＝BURST の `isUp` 脱落まで同時に直った）。
- ⚠**`manualEffects.ts` のトップレベル効果は `MANUAL` か `PARTIAL` のみ**（`AUTO` と書くと `manual-fields` ゲートが exit 1）＝`mergeManualEffects` は `parseStatus` を見ず effectId 一致で常に manual 側を勝たせるので、`AUTO` の手書きコピーは **parser の最新出力を永久に上書きし続ける**。
- ⚠**`build:effects` は破壊的ではない**（curated は温存され、`heldReview --adopt` で明示採用したものだけが変わる）。正しい規律は「実行禁止」ではなく**「実行後に effectId 単位で全数比較して、意図した件数だけが変わったことを確認する」**（出力は minified 1行なのでテキスト diff は役に立たない）。
- ⚠**カード単位 PRESERVE で held に載らない効果**（同居効果が MANUAL 等）は `build` では直せない＝`effectId` をアンカーにした**外科パッチ**で JSON を直接訂正する。共有関数にカード固有テーブルを埋めるのは禁止。

- 🆕🔴**held の原因は「消えた／変わった／増えたリーフ」を機械で出してから読む**（2026-09-06・`O-262`）＝
  `WX20-053` は**変わったリーフが `parseStatus` の1つだけ**（AUTO→PARTIAL）で、それが `isPureSuperset` の
  唯一の不一致になり **`trashActivated:true` を持つ fresh を採用できず held に居座っていた**。
  🔴**その PARTIAL は偽だった**＝`markSilentFallback` は**捨てられたパース試行からも刻まれる**ので、
  **最終 JSON に痕跡が1つも無いのに刻印だけ残る**（本件は `SEARCH.afterSearch` へ既に畳まれた文）。
  ⇒ 🔑**「採用は凍結と引き換え」なら、採用ではなく刻印の原因を消す道を先に探す**
  （`heldReview --adopt` で採ると live が PARTIAL/MANUAL になり、以後 parser 改善が永久に届かない）。
- 🆕**live が全 AUTO のカードは「配列まるごと」`isPureSuperset` に掛かる**＝`manualEffects.ts` へ手書きしても
  **1リーフでも既存値を変えると held に落ちて live に届かない**。⇒ **`npx tsx scripts/syncManualLive.ts --effect <CardNum>:<EffectId>`**
  で**その効果だけ**を届ける（カード単位で書くと、同じカードの他の効果で live のほうが新しい分を巻き戻す）。


- 🔴🆕**手書き shadow の `effectId` が live とズレるとカードごと凍る**（`O-93`・第179バッチ／旧 PLAN §5.3 から移設）＝
  `manualEffects.ts` 側が **`-E1b` / `-E2b` の枝番**で、**live の効果番号が原文の文の並びから1つズレて**いたため、
  カードが `_idset_fresh` に落ちて**そのカードへの parser 改善が何ひとつ届かなくなっていた**（実測21効果）。
  🔑**その凍結が実バグを6件隠していた**（「４つから２つ選ぶ」が1つしか選べない／相手のライフを増やす／
  keyword が UI と一致せず恒久 no-op ほか）＝**凍結は「変わらない」ではなく「壊れたまま固定される」。**
  ⚠**計器自身も嘘をつきうる**＝`censusManualDrift` は `buildEffectsJson` が**マージ後に重ねる印字キーワードコスト**を
  再現しておらず、乖離57効果のうち **36効果（63%）が偽陽性**だった。**乖離を読む前に計器の再現忠実度を疑う。**

### 4.6 Codex へ委譲するときの作法

- ⚠**Codex は実行できない**（サンドボックスのネットワーク遮断）＝**起案だけさせて、実行・判定は必ず引き取る。** 指示書の冒頭でそれを明言する。
  🔑**実機シナリオでも同じ**＝起案だけさせて実行・判定は検証側が引き取る（事故台帳は `CODEX_GUIDE.md` §5.5・続き460〜468）。
- ⚠**Codex の修正提案は分類の根拠であって実装指示ではない。** 条件を JSON へ足す前に、**その timing の collector が self スコープでそのフィールドを読むか**を必ず確認する（読まないと条件が効かず過剰実行のまま）。
- ⚠**判定の誤りは「クラスタの共通根拠を、構造の違う1件へそのまま適用する」形で出る**＝クラスタ単位の結論は**構造が同じことを1件ずつ確かめてから**採る。
- ⚠**1バッチ 20クラスタ／40 findings 前後を厳守**（107件を投げたバッチは根拠がテンプレート化して証拠にならなかった）。**件数を減らして1件ごとの証拠を厚くするほうが総合的な収量は高い。**
- ⚠**投入前に必ず `git status --porcelain` を空にする**（計器の生成時刻1行の差分で Codex が起動を拒否した実績）。
- **投入コマンド**＝`codex exec -C "C:/Users/zerom/source/WixossReact" -c model_reasoning_effort="high" -o <report> - < <指示書> > <log> 2>&1`。⚠**既定は `model_reasoning_effort = "low"` なので `-c` の指定は必須**。⚠**`-c sandbox_mode=…` は "danger" 文字列で分類器に弾かれるので付けない**。詳細は [CODEX_GUIDE.md](./CODEX_GUIDE.md)。
